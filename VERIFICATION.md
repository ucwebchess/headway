### 13.8 Bugfix: ipywidgets private-API compatibility (0.3.1)

A real defect was observed by the project owner when running the notebook end-to-end in Google
Colab: sections **5 · Self-check** and **7 · Launch the application** both stopped with

```text
ImportError: cannot import name '_instances' from 'ipywidgets.widgets.widget'
(/usr/local/lib/python3.13/dist-packages/ipywidgets/widgets/widget.py)
```

**Cause.** `railway_headway_sim/ui/table_editor.py` imported `_instances`, a *private*
attribute of `ipywidgets`, and read it in the helper `_deregister` to drop a replaced widget
from the library's widget registry. A private library internal is not part of the public API
and is not present in every `ipywidgets` version, so the import failed before any UI work
started. Depending on a private attribute of a third-party library is not defensible in a
delivered artefact.

**Fix — `railway_headway_sim/ui/table_editor.py` is the only file changed.** The private import
and the private registry access are gone. `close_widget_tree` now walks the widget tree with
the documented public attributes only — `children` of a container, the `layout` / `style`
widgets a widget carries (they are widgets too), and `value` when it holds another widget — and
releases each widget through its own public `Widget.close()` method, which closes the widget's
comm and removes it from the registry. Children are closed before their container and every
widget exactly once per call (a styling widget shared by two rows is closed once). The walk
never consults the widget's `parent` link, which is not available in every `ipywidgets`
version, and the function is safe on a leaf, on a container whose children are containers, on
an already-closed widget and on a widget that exposes no `children`. The helper keeps its name
`_deregister`; only its body changed. No private `ipywidgets` name is imported or read anywhere
in the package. Measured on the record environment: a 10-widget tree leaves 0 entries behind
after closing, and 25 rebuild-and-close cycles of a 20-row table leave the registry flat — the
memory behaviour the original code existed for is preserved.

**New regression tests — no existing test changed, removed, renamed, weakened or skipped.**
`TEST P3-025` parses every `.py` file under the package with `ast` and fails, naming file and
line, on any `from ipywidgets… import _name`, any `from ipywidgets… import *`, and any attribute
access on a name imported from `ipywidgets` whose attribute starts with `_`. The defect is
caught: with the historical line restored in a scratch copy of the package the scan reports
`ui/table_editor.py:22: from ipywidgets.widgets.widget import _instances`. `TEST P3-026` builds a
real nested widget tree, monkey-patches the public `Widget.close` to count calls, and asserts
that `close_widget_tree` closes every widget of the tree exactly once without raising, that a
repeated call does not raise either, and that a leaf widget is safe. The Phase-3 suite is 26
collected items and the four suites total `66 + 30 + 5 + 26 = 127`, all `PASS`.

### 14.9 Phase-4A correction #2 (0.4.2) — one physical corridor, two directions (observed)

**The defect.** The companion file delivered with 0.4.1 declared two paths that were **not** the
same physical corridor traversed in opposite directions: `PATH-H1-F` was an 18-edge / 47 400.0 m
walk through the Valley P2 platform road, starting on the Alpha P2 platform edge, while
`PATH-H1-R` was a 17-edge / 49 000.0 m walk through the Valley through road THRU2, ending on the
Alpha P1 platform edge. The two declarations therefore described two different railways: they
differed in which Valley edges they used and in which Alpha platform edge they ran between, and
their route lengths differed by 1 600 m. FORWARD and REVERSE of one corridor mean the **same
physical edges** traversed in opposite route order with complementary traversal values, so that
one physical railway produces a route distance 0 → L in both directions; two different corridors
cannot demonstrate that property. Left uncorrected, Stage 4B would read elevation, gradient and
curve data along two different physical alignments and label both "H1", and every downstream
phase that uses these paths would inherit that error.

**The rule used to select the single corridor (stated verbatim in the file's own `notes`).**
*Start candidates: every edge of the frozen project on which an Alpha station platform is
declared (platform.track_id). End candidates: every edge on which a Delta station platform is
declared. Among all Alpha → Delta walks of the frozen graph whose first edge is a Start
candidate and whose last edge is an End candidate, choose (a) the walk of minimum total
length_m, then (b) the walk of minimum edge count, then (c) the walk whose ordered edge-id list
is lexicographically smallest.* Applied to the frozen project this gives Start candidates
`TR-A-E1-E` (platform `PLT-ALP-P2`) and `TR-A-W-U1` (platform `PLT-ALP-P1`) and End candidate
`TR-D-P1` (platform `PLT-DEL-P1`). The minimum admissible total length is **47 400.0 m**; an
exact-length dynamic program over the frozen graph shows that no walk of 13 or fewer edges
reaches 47 400.0 m ending on an End candidate, that 14 edges do, and that exactly one such walk
exists, so the lexicographic tie-break is vacuous. The selected corridor is

```
TR-A-E1-E  → TR-O-ALP-CEN-ML1 → TR-C-W-LDR-ML1 → TR-C-XA-P4 → TR-C-P4 → TR-C-P4-E-CON →
TR-O-CEN-VAL-SL-B → TR-V-THRU2 → TR-V-T2B-E → TR-O-VAL-DEL-ML1 → TR-D-W-THR → TR-D-THR-J →
```

### 19.4 The frozen effort model and the transition speed

The characteristic is the frozen `FORCE_THEN_POWER_LIMITED` pair, with no free parameter:

```text
v_t = P * 1000 / (F_max * 1000)          [m/s]   transition speed
v   = speed_kmh / 3.6                    [m/s]
F   = F_max * 1000                       [N]     while v <= v_t   (force-limited)
F   = P * 1000 / v                       [N]     above v_t        (power-limited)
```

so `transition_speed_kmh(F_max, P) = v_t * 3.6`. For the frozen pair
`P = 9800.0` kW, `F_max = 300.0` kN: `v_t = 32.666666666666664` m/s and
**`v_t * 3.6 = 117.6` km/h exactly**; at the boundary the two branches agree exactly
(`P * 1000 / v_t = 300000.0` N), and `117.6 / 3.6` is `<= v_t`, which is why 117.6 km/h is
force-limited. `TEST P6-030` asserts the value within a relative 1e-9 and
`TEST P6-029` sweeps 0.0 … 400.0 km/h in steps of 0.5 to assert the cap always holds.
